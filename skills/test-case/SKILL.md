# Test Case

เขียนให้คนที่เปิดแค่หน้าจอรันได้ทันที: อ่านชื่อเคสแล้วรู้ว่าจะพิสูจน์อะไร อ่าน Expected แล้วรู้ว่าต้องเห็นอะไรบนจอ ไม่ต้องเปิดฐานข้อมูล ไม่ต้องเดา

## 1. โครงสร้างหนึ่งเคส

| ช่อง | ใส่อะไร |
|---|---|
| ID | `<หน้า>-<หมวด><ลำดับ>` เช่น `BK-A03` |
| Test Case | ชื่อเคส (ข้อ 2) |
| Type | Positive / Negative / Edge |
| Test Data | ค่าทั้งหมดที่ใช้ในเคส บรรทัดละช่อง `ป้าย: ค่า` |
| Pre-Condition | สิ่งที่ต้องเตรียมก่อนรัน ขึ้นต้น `ต้องเตรียม:` ไม่มีให้ใส่ `-` |
| Step | ลำดับการกระทำ (ข้อ 4) |
| Expected Result | สิ่งที่ต้องเห็น (ข้อ 5) |
| Result / Remark | คนรันกรอก: Pass / Fail / Block / N/A และเลข ticket ถ้ามี |

## 2. ชื่อเคส

รูปแบบเดียวทุกเคส: `ตรวจสอบกรณี <สถานการณ์> <สิ่งที่ต้องพิสูจน์>`

- ขึ้นต้น `ตรวจสอบกรณี` เสมอ บรรทัดเดียว ไม่เกิน ~80 ตัวอักษร
- ใช้คำตามป้ายบนหน้าจอจริง ไม่ใช้ชื่อตัวแปรหรือศัพท์โค้ด
- บอกสิ่งที่พิสูจน์ ไม่ใช่สรุปผล รายละเอียดผลลัพธ์อยู่ที่ Expected เท่านั้น
- ท้ายประโยคตามชนิดเคส:

| ชนิด | ปิดท้าย |
|---|---|
| Negative บนหน้าจอ | `ต้องมี Validate` |
| Negative ยิง API ตรง | `ต้องถูกปฏิเสธ` |
| Positive | จบที่การกระทำ เช่น `แล้วบันทึก` |
| Edge เรื่องค่าค้าง | `ต้องไม่ค้าง` / `ค่าต้องยังอยู่` |

ตัวอย่าง (ระบบจองห้องประชุม): `ตรวจสอบกรณี จองห้องในช่วงเวลาที่มีคนจองแล้ว ต้องมี Validate`

## 3. หมวดความครอบคลุม

ทุกหมวดฟีเจอร์ควรไล่ให้ครบ ห้ามเขียนเคสที่รันไม่ได้เพียงเพื่อให้ครบชนิด

| หมวด | ตัวอย่างในฟอร์มสมัครสมาชิก |
|---|---|
| Positive | กรอกครบถูกต้องแล้วสมัครสำเร็จ |
| Negative | เว้นช่องบังคับ, อีเมลรูปแบบผิด, อีเมลซ้ำ |
| Boundary | รหัสผ่านสั้นสุด/ยาวสุดที่ยอมรับ, สั้นกว่า 1 ตัวอักษร, วันเกิดวันนี้ |
| Permission | role ที่ไม่มีสิทธิ์เข้าไม่ได้, ดูอย่างเดียวแก้ไม่ได้, ข้อมูลผู้ใช้อื่นไม่รั่ว |
| Data | บันทึกแล้วรีเฟรชค่ายังอยู่, ค่าเดิมไม่เปลี่ยนเมื่อยกเลิก, ตัวอักษรพิเศษ/ภาษาไทย/ข้อความยาว |
| Flow ล้มกลางทาง | ปิดหน้าระหว่างบันทึก, session หมดอายุ, กดซ้ำสองครั้ง |

หน้าที่มีช่องค้นหาหรือตัวกรอง ต้องมีเคสทุกช่อง ทั้งทีละช่องและรวมกัน ค่าที่ไม่พบผล และปุ่มล้างตัวกรอง
ฟอร์มที่มีช่องเลือกจากข้อมูลหลัก (master) ต้องมีเคสว่าค่าที่เลือกไว้ยังอยู่หลังบันทึกและเปิดดูใหม่

## 4. Test Data และ Step

- **Test Data เก็บค่า** (บัญชีที่ใช้ ค่าที่กรอกหรือเลือก) **Step บอกแค่การกระทำกับชื่อช่องบนจอ** ไม่ใส่ค่าซ้ำ
- ค่าต้องเป็นค่าจริงที่มีในระบบทดสอบและเห็นบนจอ ไม่มีคำบรรยายต่อท้าย ไม่มี placeholder เช่น `<อีเมล>`
- ข้อละหนึ่งการกระทำ ใช้กริยาสั้น (`กรอก ชื่อ`, `เลือก ห้อง`, `กด บันทึก`)
- ข้อแรกรวม Login กับเปิดเมนู: `Login แล้วเปิดเมนู จองห้อง > สร้างการจอง`
- `ตรวจสอบหน้าจอ` มีได้ข้อเดียว **เป็นข้อสุดท้าย** ถ้ามีหลายจังหวะ (บันทึก, รีเฟรช, สลับบัญชี) ให้บอกจังหวะใน Expected

```
Test Data: Login: member01
           ห้อง: Room A
           วันที่: พรุ่งนี้
✅ 1. Login แล้วเปิดเมนู จองห้อง > สร้างการจอง
   2. เลือก ห้อง
   3. เลือก วันที่
   4. กด บันทึก
   5. ตรวจสอบหน้าจอ
```

## 5. Expected Result

บรรทัดแรกคือ `หน้าจอต้องแสดง` แล้วไล่สิ่งที่เห็นบนจอเป็น bullet `- `

```
หน้าจอต้องแสดง
- ข้อความ บันทึกข้อมูลเรียบร้อย หลังกด บันทึก
- รายการจองใหม่อยู่ในตาราง หลังรีเฟรชหน้า
```

- สั้น 1-3 bullet บอกเงื่อนไขที่ผลต้องตรง ไม่ไล่รายการรหัสทีละตัว ใช้ป้ายและค่าเดียวกับ Test Data
- ห้ามอ้างเลขข้อของ Step ให้บอกจังหวะเป็นคำท้าย bullet แทน
- ห้ามขึ้นต้น bullet ด้วย "หน้าจอแสดง" ซ้ำ ห้ามเขียน "ถ้า... ถือว่าไม่ผ่าน" ซ้ำกับ bullet เว้นแต่อาการผิดดูไม่ออกจาก bullet
- เคสผ่านหน้าจอ ห้ามใส่ query ชื่อตาราง ชื่อคอลัมน์ อยากพิสูจน์ว่าบันทึกจริงให้ใช้ Step `รีเฟรชหน้า` แล้วตรวจจอ
- ข้อยกเว้นเดียว: เคสยิง API ตรง ตรวจจาก response ได้ ขึ้นบรรทัดแรกว่า `response ต้องปฏิเสธพร้อมข้อความ ...` และแยกไว้หมวด "ตรวจฝั่งเซิร์ฟเวอร์"

## 6. แต่ละเคสต้องจบในตัวเอง

- ห้ามอ้าง ID เคสอื่นใน Pre-Condition, Step หรือ Expected
- ต้องใช้ข้อมูลที่เคสอื่นสร้าง ให้ใส่ขั้นสร้างข้อมูลนั้นใน Step ของเคสนี้
- เตรียมผ่านหน้าจอไม่ได้ ให้เขียน Pre-Condition เป็นสภาพที่ต้องมี (`ต้องเตรียม: มีการจองห้อง A เต็มทั้งวัน`)
- เลือกบัญชีและข้อมูลให้ตรงเงื่อนไขธุรกิจของเคส (role ถูก สถานะข้อมูลถูก ณ วันที่รัน) ไม่งั้นได้ Fail ที่ไม่ใช่บั๊ก

## 7. Summary ของโมดูล

เมื่อเขียนเคสครบทุกหน้า ให้ทำชีตสรุปหนึ่งไฟล์ต่อโมดูล

- แถวละหน้าจอ: ชื่อหน้า (ลิงก์ไปไฟล์เคส), ผู้พัฒนา, เลข ticket, สถานะพัฒนา, สถานะทดสอบ, Tester, Remark
- ตัวเลข: จำนวนเคส, Pass, Fail, ยังไม่ทดสอบ, % ที่ทดสอบแล้ว ดึงสดจากชีตเคสด้วยสูตรเพื่อไม่ต้องอัปเดตมือ
- แท็บ Issue ที่ยังเปิดอยู่: รวมรายการ Fail ของทุกหน้าที่ยังไม่ปิด พร้อมสถานะจากระบบ ticket
- ช่องที่คนกรอกเอง (Tester, สถานะทดสอบ) ห้ามให้สูตรหรือสคริปต์เขียนทับ
- ถามเจ้าของงานก่อนสร้างหรือแก้ Summary เสมอ

## 8. ตอนแก้ชีตที่ทีมใช้อยู่

- ก่อนเขียน บอกเป้าหมายหนึ่งบรรทัด: ชื่อไฟล์ แท็บ หมวดหรือแถว ข้อไหนเดาให้ถามก่อน
- เขียนเฉพาะคอลัมน์เนื้อเคส ห้ามแตะ Actual Result / Result / Remark ที่คนอื่นกรอกไว้
- แก้ทีละหมวด อ่านกลับทุกช่องหลังเขียน แล้วแสดงตัวอย่างก่อน/หลัง

## 9. เช็คก่อนส่ง

- [ ] ชื่อเคสขึ้นต้น `ตรวจสอบกรณี` บรรทัดเดียว ไม่มีค่าละเอียดและไม่มีศัพท์โค้ด
- [ ] Test Data มีเฉพาะบัญชีกับค่าที่กรอกหรือเลือกจริง เป็นค่าที่มีบนจอ
- [ ] Step ข้อละหนึ่งการกระทำ ไม่ซ้ำค่า และ `ตรวจสอบหน้าจอ` มีข้อเดียวเป็นข้อสุดท้าย
- [ ] Expected ขึ้นต้น `หน้าจอต้องแสดง` 1-3 bullet ไม่อ้างเลขข้อ ไม่มี query
- [ ] ทุกเคสรันเดี่ยวได้ ไม่อ้าง ID เคสอื่น
- [ ] หมวดที่ฟีเจอร์ครบแล้วมี Positive / Negative / Edge และมี Boundary, Permission, Data ตามที่เกี่ยวข้อง
- [ ] ทุกช่องค้นหา/ตัวกรอง และทุกช่องเลือกจากข้อมูลหลัก มีเคสครบ
- [ ] อ่านกลับจากชีตแล้วตรงกับที่ตั้งใจเขียน
