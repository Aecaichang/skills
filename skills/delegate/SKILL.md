# Delegate: แบ่งงานให้ subagent ตามประเภทงาน

โมเดลหลักคิด ตัดสินใจ และตรวจผล งานที่ทำซ้ำได้และตรวจได้ด้วยสคริปต์ส่งให้ subagent รุ่นที่ถูกกว่า
ได้สองอย่าง: ค่าใช้จ่ายลดลง และไฟล์ใหญ่ไม่กิน context ของงานหลัก

## 1. ส่งได้ไหม

ส่งเองได้โดยไม่ต้องรอผู้ใช้สั่ง เมื่อครบทั้ง 3 ข้อ ขาดข้อเดียวให้ทำเอง

- **ขอบเขตชัด:** รู้เป้าหมาย และมีวิธีเช็กว่าเสร็จ
- **งานหนัก:** ต้องเรียกเครื่องมือหลายรอบ อ่านไฟล์ใหญ่ หรือผลลัพธ์ยาว งาน 2-3 คำสั่งทำเองถูกกว่า การส่งงานก็มีต้นทุน
- **พลาดแล้วเสียหายน้อย:** จับความผิดได้ง่าย หรือโมเดลหลักตรวจก่อนเอาผลไปใช้

## 2. เลือกรุ่น

เลือกรุ่นต่ำสุดที่ยังทำงานนั้นได้

| รุ่น | `model` | งาน |
|---|---|---|
| Haiku | `"haiku"` + `effort: "low"` | งานกลไกที่สคริปต์ตรวจได้: รันเทสแล้วเก็บผล, คัดแถว FAIL เป็น JSON, หาโค้ด (file:line, ใครเรียกใคร), ดึงหรือแปลงข้อมูล xlsx/json/csv, สรุป log, แก้ไฟล์จำนวนมากตามแพทเทิร์นที่มีคำสั่งเช็ก |
| Sonnet | `"sonnet"` | งานร่างที่ต้องใช้วิจารณญาณ: เขียนแถว Test Case, ร่างหน้าคู่มือ, วาดไดอะแกรม, ไล่หาจุดคุณภาพโค้ด, แก้ไฟล์เดียวที่มีเทสยืนยัน |
| โมเดลหลัก | ทำเอง | ขอบเขตไม่ชัด, หาต้นเหตุข้ามหลายระบบ, ตรรกะเงินหรือสิทธิ์, เทียบ spec กับโค้ด, ตัดสินว่าเป็นบั๊กหรือไม่, ตรวจผล subagent รอบสุดท้าย |

- **อ่านไฟล์ใหญ่เพื่อหยิบไม่กี่ข้อ ส่ง Haiku:** ให้อ่านแล้วส่งกลับแค่บรรทัดที่ต้องใช้พร้อม file:line ประหยัด context มากกว่าส่งงานเขียน
- **ค้นหาอย่างเดียว** ("X อยู่ไหน", "ใครเรียก Y") ใช้ agent แบบอ่านอย่างเดียว เช่น `Explore` กับ `model: "haiku"`
- **Haiku ห้าม:** ตัดสินว่าเป็นบั๊กหรือไม่ และเขียนข้อความที่ส่งถึงลูกค้าหรือลงเอกสารจริงของทีม

### Agent สำเร็จรูป (`agents/`)

ตั้งชื่อตามงาน ล็อกรุ่นไว้ใน frontmatter เรียกด้วย `subagent_type` แล้วส่ง brief ตามข้อ 3 เหมือนเดิม

| agent | รุ่น | งาน |
|---|---|---|
| `test-runner` | Haiku | รันเทส ส่ง FAIL เป็น JSON |
| `big-file-reader` | Haiku | อ่าน xlsx/log/โค้ดใหญ่ ส่งแค่บรรทัดที่ถามพร้อมที่มา, แปลงข้อมูล |
| `code-scanner` | Sonnet | สแกนคุณภาพโค้ดทีละโฟลเดอร์ อ่านอย่างเดียว |

ติดตั้ง: `ln -s <path-ของ-repo-นี้>/skills/delegate/agents/*.md ~/.claude/agents/`
งานที่ไม่ตรงกับ agent ไหน ใช้ `general-purpose` หรือ `Explore` กับ `model` ตามตารางข้างบน อย่าเพิ่ม agent ตามบทบาท (frontend, backend…)

## 3. เขียนคำสั่ง

subagent ไม่เห็นบทสนทนา คำสั่งต้องครบในตัว ใช้หัวข้อนี้ทุกครั้ง

```
GOAL: ผลลัพธ์ที่ต้องการ ประโยคเดียว
STATE: ตอนนี้งานอยู่ตรงไหน รู้อะไรแล้ว
SOURCES: path ไฟล์ ลิงก์ ที่ต้องอ่าน และอันไหนห้ามแก้
CONSTRAINTS: ห้ามทำอะไร (ห้าม commit ห้าม deploy ห้ามแตะโฟลเดอร์อื่น)
TOOLS: เครื่องมือหรือสคริปต์ที่ควรใช้
DONE: คำสั่งเช็กที่ต้องรันผ่านก่อนบอกว่าเสร็จ
RECEIPT: แก้อะไรไป, เช็กอะไรจริงและผลเป็นยังไง, อะไรยังไม่ยืนยัน, อะไรค้าง
```

"เสร็จ" โดยไม่มีผลเช็ก ถือว่ายังไม่เสร็จ

## 4. ตรวจผล

1. รันสคริปต์ตรวจผลทุกแถว (นับแถว เทียบค่า grep คำต้องห้าม รันเทส) อย่าเชื่อใบรับงานอย่างเดียว
2. โมเดลหลักสุ่มดู 3-5 รายการ ไม่ตรวจซ้ำทุกแถว ไม่อย่างนั้นที่ประหยัดมาก็หาย
3. Haiku ไม่ผ่านเช็ก 1 ครั้ง ทำใหม่ด้วย Sonnet
4. Sonnet ไม่ผ่าน 2 ครั้ง โมเดลหลักทำเองพร้อมหลักฐานว่าพลาดตรงไหน อย่าสั่งรุ่นเดิมซ้ำด้วยคำที่แรงขึ้น

## 5. ข้อห้าม

- งานที่ออกไปข้างนอกหรือย้อนไม่ได้ (เปิดการ์ด push deploy อัปโหลด เขียนลงชีตจริง) โมเดลหลักทำหลังผู้ใช้ยืนยัน subagent ทำได้แค่ร่าง
- รัน subagent พร้อมกันไม่เกิน 1-2 ตัว ตัวที่ไม่ต้องรอผลให้รันเบื้องหลัง
- บอกผู้ใช้หนึ่งบรรทัดว่างานไหนส่งให้รุ่นไหน
- งานยาวที่โมเดลหลักไม่ต้องใช้ผลกลับมา (เขียนชีตทั้งชีต ทำคู่มือทั้งโมดูล) แนะนำผู้ใช้เปิด session ใหม่ด้วยรุ่นกลางแทน

## 6. จดบันทึก

หลังตรวจใบรับงานแล้ว ต่อท้ายไฟล์ `~/.claude/subagent-log.tsv` หนึ่งบรรทัด คั่นด้วย tab:

```
date	project	model	task	check-run	result(pass|fail|escalated)	user-fix(yes|no|?)
```

`user-fix` = ผู้ใช้ต้องแก้ผลเองไหม ไม่รู้ใส่ `?` แล้วกลับมาแก้ถ้าผู้ใช้แก้ทีหลัง
อ่านไฟล์นี้ตอนจะปรับเกณฑ์ว่างานแบบไหนส่งรุ่นไหนได้จริง

ถ้าโมเดลหลักแก้งานก่อนส่ง ให้เขียนในช่อง result ว่าแก้อะไร เช่น `pass (Opus fixed: a remark leaked into the Expected column)`
ข้อ 7 ใช้ช่องนี้หาเรื่องที่ต้องแก้ซ้ำ

## 7. เปลี่ยนเรื่องที่แก้ซ้ำเป็นสคริปต์ตรวจ

ถ้าโมเดลหลักต้องแก้เรื่องเดียวกันตั้งแต่ 2 ครั้งขึ้นไป อย่าเขียนกฎเพิ่มใน prompt ให้แรงขึ้น รุ่นเล็กจะพลาดซ้ำ
ให้เพิ่มเป็นข้อตรวจในสคริปต์ตรวจของสกิลนั้นแทน (สคริปต์ที่รันตรวจผลงานนั้นอยู่แล้ว)
รอบหน้า subagent รันสคริปต์แล้วเห็น ✗ ก็แก้เองได้ก่อนส่ง โมเดลหลักไม่ต้องแก้ให้

ดูเรื่องที่แก้ซ้ำ:

```bash
awk -F'\t' '$6 ~ /Opus|fix|round/' ~/.claude/subagent-log.tsv
```

ก่อนเพิ่มข้อตรวจ รันสคริปต์กับไฟล์ที่ตรวจผ่านแล้วหลายๆ ไฟล์ ข้อตรวจที่ดีต้องเจอแค่ไม่กี่เคสและเป็นปัญหาจริงทุกเคส
เรื่องที่ต้องใช้วิจารณญาณ (เลือกเคสไหนเหมาะกับลูกค้า ข้อความแบ่งตรงไหน) เขียนเป็นข้อตรวจไม่ได้ ให้โมเดลหลักตรวจเองต่อไป
