# UAT Test Script สำหรับส่งลูกค้า

Test Script คือเอกสารที่ลูกค้าใช้ทดสอบระบบด้วยตัวเองก่อนรับมอบงาน ผู้อ่านไม่ใช่นักพัฒนา
ต้องอ่านแล้วทำตามได้ทันทีโดยไม่ต้องรู้จักระบบมาก่อน ส่งมอบเป็น Excel 1 ฟีเจอร์หรือ 1 โมดูลต่อ 1 ไฟล์

## หลักการ

- เขียนจาก spec หรือ requirement เป็นเคสใช้งานจริงแบบ end-to-end ไม่ต้องรอ test case ภายในผ่านครบ
- 1 เคส = 1 เส้นทางธุรกิจครบวง เช่น ผู้ใช้ยื่นคำขอ, ผู้อนุมัติอนุมัติ, ผลที่เห็นของทั้งสองฝั่ง
  เคสที่ตรวจแค่หน้าตาหรือแค่ตัวกรองให้น้อยลง ใช้เมื่อเป็นเงื่อนไขสำคัญของ spec เท่านั้น
- เขียนเฉพาะสิ่งที่ผู้ใช้ทำได้จริงบนหน้าจอ ตัดการยิง API, DevTools, การแก้ฐานข้อมูล
- ห้ามส่งเคสที่ยังไม่เคยลองรันจริง ถ้าข้อความระบบหรือชื่อปุ่มยังไม่ยืนยัน ให้ตรวจกับหน้าจอจริงก่อน
- ถ้า spec ขัดกับของจริง นั่นคือเรื่องรายงานบั๊ก ไม่ใช่เรื่องของไฟล์นี้ ห้ามแก้เคสให้เข้ากับบั๊ก
- เรื่องภายใน (ชื่อฐานข้อมูล, endpoint, รหัสภายใน, บั๊กที่เจอ, ชื่อไฟล์ spec) ห้ามอยู่ในไฟล์ที่ส่ง

## โครงไฟล์

ชีตเรียงตามนี้: Cover, Change Record, Summary, Test Plan, ชีตเคส (1 ชีต = 1 หัวข้อย่อย), Notes (ถ้ามี)

หัวตารางชีตเคส (ตรึงแถวหัวตาราง):

| Test Case No. | Sub-Module | User Story Topic | Scenario Description | Pre-Condition | Test step | Expected result | Pass/Fail | Result | Test by | Start Test Date | End Test Date | Remark |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

ลำดับ Pre-Condition, Test step, Expected result อ่านตามจังหวะทดสอบ: เตรียม, ทำตามขั้น, ดูผลที่อยู่ติดกัน

## กติกาการเขียนเคส

- **เลขเคส** `UAT-<รหัสโมดูล><เลข sub>-<3 หลัก>` เช่น `UAT-BK1-001` เรียงต่อเนื่อง ไม่ข้าม ไม่ซ้ำ
- **User Story Topic** หัวข้อหลักตามด้วยกรณีย่อยหลัง `/` เช่น `สมัครสมาชิก / Validation อีเมลไม่ถูกต้อง` ห้ามซ้ำกันเป๊ะหลายแถว
- **Scenario Description** ขึ้นต้นด้วยคนทำ เช่น `ผู้ดูแลระบบสามารถ...` หรือ `ตรวจสอบว่า...`
- **Pre-Condition** ข้อ 1 คือกลุ่มผู้ใช้ที่ต้องล็อกอิน ข้อถัดไปคือข้อมูลที่ต้องมีอยู่ก่อน
  อย่าใส่ชื่อผู้ใช้ รหัสผ่าน อีเมล หรือรหัสพนักงานจริงในไฟล์
- **อ้างข้อมูลที่มีอยู่ด้วยคำกลาง** เพราะเครื่องของลูกค้ามีข้อมูลคนละชุดกับเครื่องที่เราทดสอบ
  - Pre-Condition: `มีห้องประชุมที่เปิดให้จองอย่างน้อย 1 ห้อง` ไม่ใช่ `ห้อง Room-A มีอยู่`
  - Step: `เลือกห้องใดก็ได้ แล้วจดชื่อห้อง` ไม่ใช่ `เลือกห้อง Room-A`
  - Expected: `ชื่อห้องตรงกับที่เลือก` ข้อมูลที่เคสสร้างเองตั้งชื่อได้
- **Test step** 3-6 ข้อ 1 ข้อ = 1 การกระทำ ข้อสุดท้ายเป็นการตรวจสอบเสมอ
  เคส validation เขียนครบวง: กรอกผิด, เห็น error, แก้ให้ถูก, บันทึกสำเร็จ
- **Expected result** ลูกค้าอ่านแล้วตัดสินได้ทันทีว่าผ่านไหม บรรทัดแรก `หน้าจอต้องแสดง` ตามด้วย bullet 1-2 ข้อ ข้อละไม่เกิน 1 บรรทัด

```
หน้าจอต้องแสดง
- ข้อความ "จองห้องสำเร็จ"
- รายการจองใหม่อยู่ในหน้ารายการของฉัน หลังรีเฟรชหน้า
```

  - บอกเฉพาะผลที่ลูกค้ามองหา: ข้อความที่ขึ้น, ข้อมูลที่เปลี่ยน, สิ่งที่ต้องไม่เห็น
  - ใช้คำธรรมดา ไม่ใช้ศัพท์ระบบ ไม่ลิสต์ชื่อคอลัมน์ยาวๆ
  - ข้อความระบบใส่เครื่องหมายคำพูด ยกแค่ต้นประโยค ชื่อปุ่มและชื่อช่องไม่ต้องใส่
  - พิสูจน์ว่าบันทึกจริงด้วย `หลังรีเฟรชหน้า` ห้ามอ้างฐานข้อมูล
  - เกิน 2 ข้อ แปลว่าเคสตรวจหลายเรื่อง ให้แยกเป็นหลายเคส
- **สถานะ** มี 3 ค่า: `Wait test` (ยังไม่ทดสอบ), `Pass` (ตรง Expected), `Fail` (ไม่ตรง บอกสิ่งที่เห็นใน Remark)
  ไฟล์ที่ส่งต้องเป็น `Wait test` ทุกเคส Pass/Fail ว่าง ห้ามส่งไฟล์ที่มาร์ค Pass ไว้แล้ว
- **Remark** ใช้บอกข้อจำกัดที่คนทดสอบต้องรู้ เช่น สิทธิ์ใหม่มีผลหลังออกจากระบบแล้วเข้าใหม่

## บัญชีที่ใช้ทดสอบ

ลูกค้าทำ UAT ด้วยผู้ใช้จริงของแต่ละกลุ่มสิทธิ์ ไม่ใช่บัญชีผู้ดูแลสูงสุดที่เห็นทุกเมนู
1. ดูตารางสิทธิ์ (permission matrix) ว่าเมนูของเคสอยู่กลุ่มไหน
2. ระบุกลุ่มใน Pre-Condition เช่น `เข้าสู่ระบบด้วยผู้ใช้กลุ่ม เจ้าหน้าที่ห้องประชุม (ระบุจากตารางสิทธิ์)`
3. ตอนรันภายในใช้บัญชีที่มีสิทธิ์ตรงกลุ่มนั้นจริง ห้ามรันด้วยบัญชีผู้ดูแลสูงสุดแล้วเขียนว่าเป็นกลุ่มอื่น
4. เลือกบัญชีตามเคส: เคส Admin ใช้กลุ่มผู้ดูแลเมนู, เคสยื่นคำขอใช้ผู้ใช้ทั่วไป, เคสอนุมัติใช้ผู้อนุมัติคนละคนกับผู้ยื่น, เคสไม่มีสิทธิ์ใช้กลุ่มที่ไม่มีเมนูนี้

## เคสที่ต้องมี ไม่ใช่แค่ happy path

ต่อ 1 หน้าจอ ไล่ให้ครบ: ดู, ค้นหาทุกตัวกรอง, เพิ่ม, แก้ไข, ลบ, นำเข้า/ส่งออก, สิทธิ์ตามกลุ่ม
แล้วเติมเคส negative อย่างน้อย 1 ใน 8 ของทั้งไฟล์:
- กรอกไม่ครบ, รูปแบบผิด (วันที่ ตัวเลข อีเมล), ค่าซ้ำ, ช่วงข้อมูลซ้อนทับ
- ลบข้อมูลที่ถูกอ้างอิงอยู่ ต้องถูกบล็อกหรือเตือน
- ผู้ใช้ไม่มีสิทธิ์: ไม่เห็นเมนู, เปิดลิงก์ตรงไม่ได้, ไม่เห็นปุ่มเพิ่มและลบ
- ค้นหาข้อมูลนอกขอบเขตที่ดูแล ต้องไม่พบ
- ยกเลิกกลางคันหรือออกจากหน้าโดยไม่บันทึก ข้อมูลต้องไม่เปลี่ยน

เคส negative ต้องลองรันจริงก่อนเหมือนเคสอื่น ห้ามใส่ Expected ที่เดาไว้

## Cover และ Change Record

- Cover: ชื่อโครงการ ชื่อโมดูล เวอร์ชัน วันที่ ชื่อลูกค้า (โลโก้ถ้ามี)
- Change Record ใส่เฉพาะฉบับที่ส่งจริง: วันที่ | เวอร์ชัน | ผู้แก้ | สิ่งที่เปลี่ยน (ฉบับแรกเขียน `ฉบับแรก`)
  ไม่ใส่แถวเวอร์ชันอนาคตล่วงหน้า
- Summary นับจำนวนเคสต่อชีตและสถานะ ต้องครบทุกเคส

## เช็คก่อนส่ง

- [ ] ชีตครบตามลำดับ หัวตารางตรง ชื่อโมดูลบน Cover ตรงกับชีตเคส
- [ ] เลขเคสเรียงต่อเนื่อง ไม่ซ้ำ Summary ครบทุกเคส
- [ ] Expected ขึ้นต้น `หน้าจอต้องแสดง` ไม่เกิน 2 bullet ไม่มีลิสต์ย่อย
- [ ] ทุกเคสสถานะ `Wait test` ไม่มีผลค้าง
- [ ] ไม่มีข้อมูลจริงของลูกค้า: ชื่อ รหัสพนักงาน อีเมล ลิงก์ รหัสผ่าน
- [ ] ไม่มีชื่อข้อมูลจากเครื่องทดสอบของเราค้างในเคส (ค้นชื่อที่ใช้ตอนรัน)
- [ ] ไม่มีคำค้างอย่าง `XXXX` `TBD` และไม่มีคำสะกดผิด
- [ ] ทุกเคสเคยรันตามขั้นตอนในไฟล์แล้วได้ผลตรง Expected
- [ ] ชื่อเมนู ปุ่ม ช่อง ตรงกับหน้าจอจริง
