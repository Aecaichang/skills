# QA Bug Triage

วิธีคิดและเกณฑ์ตัดสินใจ เพื่อให้ผลงานออกมามาตรฐานเดียวกัน ข้อมูลเฉพาะโปรเจกต์ให้ค้นจาก repo และ spec ตอนทำงานจริง ไม่ใช่จากความจำ

## 1. หลักคิด

1. **business ก่อน technical**: requirement ตกลงกันว่าอะไร แล้วค่อยดูว่าระบบทำตรงไหม
2. **หา gap ไม่ใช่แค่หา bug**: ช่องว่างระหว่าง requirement กับสิ่งที่ระบบทำจริงมีค่ากว่า bug เดี่ยวๆ
3. **ถามว่า "ถ้า user ทำแบบนี้จะเกิดอะไร"** โดยเฉพาะ flow ที่ล้มกลางทาง state ต้องไม่ค้าง
4. **ตัวเลขและเงินต้องพิสูจน์ด้วยข้อมูลจริง**: ดูฐานข้อมูลหรือ response จริงก่อนสรุป สิ่งที่อ่านจากโค้ดเป็นแค่สมมติฐาน
5. **ครบ 3 ด้านเสมอ**: positive, negative, edge case ขาดด้านใดถือว่ายังไม่เสร็จ
6. **ทำเท่าที่โจทย์สั่ง** ไม่แตะสิ่งที่ไม่เกี่ยว
7. **บอก assumption**: โจทย์ตีความได้หลายแบบ ให้บอกว่าเลือกแบบไหนและเพราะอะไร
8. **รายงานเปิดด้วยคำตอบ**: บรรทัดแรกคือคำตอบของเรื่องที่ถาม ตามด้วยสิ่งที่ต้องตัดสินใจ หลักฐาน แล้วรายละเอียด

## 2. เรียกว่า "บั๊ก" เมื่อครบ 3 ข้อ

| ข้อ | ต้องมี |
|---|---|
| 1 | มี spec หรือพฤติกรรมเดิมของระบบที่มันขัด อ้างได้ว่าข้อไหน |
| 2 | ผู้ใช้จริงเจอผลเสีย ไม่ใช่แค่สคริปต์ทดสอบเจอ |
| 3 | ทำซ้ำได้ |

ขาดข้อใดข้อหนึ่ง ให้เรียกว่า **ข้อสังเกต (ยังไม่ยืนยัน)** แล้วถามเจ้าของ spec ก่อนเปิด ticket
ก่อนเสนอ ให้เช็กด้วยว่าทีมเคยตัดสินแล้วหรือไม่ว่าพฤติกรรมนี้เป็นที่ยอมรับ ถ้าผลจากสคริปต์ต่างจากที่คนเห็นบนจอ ให้เชื่อจอ

## 3. Severity

| ระดับ | นิยาม |
|---|---|
| Critical | ระบบพัง, data loss, security breach, ใช้งานไม่ได้เลย |
| High | ฟีเจอร์หลักใช้ไม่ได้ มี workaround แต่รับไม่ได้ |
| Medium | ฟีเจอร์รองใช้ไม่ได้ หรือมี workaround ง่าย |
| Low | UI ผิด, typo, cosmetic |

## 4. คัดกรองปัญหาที่ลูกค้าแจ้ง

ทำตามลำดับ ขั้นเดียวที่ตัดสินผลคือ **repro** ยังไม่มี repro สาเหตุทุกข้อที่คิดคือการเดา

1. **สร้าง repro** ในสภาพแวดล้อมทดสอบ ใช้บัญชีบทบาทเดียวกับลูกค้าและข้อมูลสภาพเดียวกัน ถ้าไม่ได้ให้ลองยิง API ตรงด้วย request เดียวกัน หรือ query แบบอ่านอย่างเดียว
   เสร็จเมื่อ: ลองจริงแล้ว เห็นอาการเดียวกับที่แจ้ง (ไม่ใช่อาการใกล้เคียง) ทำซ้ำได้ (ถ้าเกิดบางครั้งให้บอกอัตรา เช่น 3 ใน 10 รอบ) และจดข้อความ error หรือค่าที่ผิดไว้ตรงตัว
   ทำไม่ได้: บอกว่าลองทางไหนแล้ว ขอเฉพาะสิ่งที่ปลดล็อก (บัญชีและข้อมูลที่ลูกค้าใช้, ภาพหรือคลิปพร้อมเวลา, log ช่วงนั้น) ระหว่างรอทุกข้อสรุปเป็นข้อสังเกต
2. **ย่อ repro**: ตัดทีละอย่าง (ขั้นตอน ตัวกรอง ข้อมูล บัญชี) แล้วลองใหม่ เหลือเฉพาะสิ่งที่ตัดแล้วอาการหาย
3. **ตั้งสมมติฐาน 3-5 ข้อ** เรียงตามความน่าจะเป็น ครอบทุกประเภท: บั๊กในโค้ด, ข้อมูลผิด, สิทธิ์หรือค่าตั้ง, requirement ไม่ตรงกัน แต่ละข้อต้องบอกผลที่คาดได้ว่า "ถ้าสาเหตุคือ X แล้วเปลี่ยน Y อาการจะหาย"
4. **พิสูจน์ทีละข้อ** เปลี่ยนทีละตัวแปร จนเหลือข้อเดียวที่มีหลักฐานยืนยัน ข้ออื่นถูกตัดด้วยหลักฐาน
5. **ตัดสินและส่งต่อ**

| ผล | ทำต่อ |
|---|---|
| บั๊ก | ผ่านเกณฑ์ 3 ข้อแล้ว เปิด ticket ด้วย repro ที่ย่อแล้ว |
| ข้อมูลผิด | บอกแถวที่ผิด วิธีแก้ จำนวนที่กระทบ และวิธีย้อนกลับ |
| สิทธิ์หรือค่าตั้ง | บอกค่าที่ต้องเปลี่ยน อยู่หน้าจอไหน ใครเปลี่ยนได้ |
| requirement ไม่ตรงกัน | อ้าง spec ที่ระบบทำตาม แล้วให้เจ้าของ requirement ตัดสิน |

6. **ตรวจหลังแก้**: รัน repro ตัวเต็ม (ไม่ใช่ตัวย่อ) อาการต้องไม่เกิด รันเคสทดสอบที่ทำจาก repro รวมถึงลอง flow ใกล้เคียง 1-2 ทางที่ใช้โค้ดหรือข้อมูลชุดเดียวกัน

## 5. Review Feature

ไล่ทุกข้อให้มีผล **ผ่าน / ไม่ผ่าน / ไม่เกี่ยว** พร้อมหลักฐาน (ภาพ, response, query) ข้อที่ตรวจไม่ได้ให้เขียนว่าติดอะไร ไม่นับว่าผ่าน

- **Business logic**: ตรง requirement, edge case ที่ business บอกถูกจัดการ, validation message เข้าใจได้
- **Data**: บันทึกถูก, คำนวณถูก (เงิน ตัวเลข), ข้อมูลที่แสดงตรงกับที่บันทึก
- **Flow**: happy path ครบ, error handling ชัด, ล้มกลางทางแล้ว state ถูกต้อง
- **Permission**: role ที่ไม่มีสิทธิ์เข้าไม่ได้, ข้อมูลของ user A ไม่รั่วให้ user B

รายงานแยกสองแกน เพราะฟีเจอร์หนึ่งผ่านแกนหนึ่งแต่ตกอีกแกนได้:

| แกน | ถามว่า | ตัวอย่าง |
|---|---|---|
| gap กับ spec | ระบบทำสิ่งที่ตกลงไว้ครบและตรงไหม | spec ให้ส่งกลับแก้ไขได้ แต่ไม่มีปุ่ม |
| บั๊ก | สิ่งที่ระบบทำ ถูกไหม | กดบันทึกแล้ว error, ยอดรวมผิด, สิทธิ์รั่ว |

เขียนเป็นสองหัวข้อ เรียง severity ภายในแต่ละแกน ปิดท้ายด้วยจำนวนรายการและเรื่องที่หนักที่สุดของแต่ละแกน ถ้าไม่มี spec ให้เทียบ ให้เขียนว่า "ไม่มี spec ให้เทียบ" แล้วถามว่า spec อยู่ที่ไหน

## 6. รูปแบบรายงานบั๊ก

```
Title: สั้น ชัด บอกอาการ
Severity: Critical / High / Medium / Low
Steps to Reproduce: 1. ... 2. ... 3. ... (ไม่เกิน 5 ข้อ)
Expected: ควรเป็นอะไร
Actual: เป็นอะไร
Environment: Dev / Staging / Prod
Evidence: ภาพ / วิดีโอ / log
```

## 7. ความปลอดภัยและขอบเขต

- ข้อมูลลูกค้าประมวลผลในเครื่องเท่านั้น ห้ามส่ง log หรือ dump ไปบริการภายนอก
- ก่อนแสดง log หรือผล query ให้ปิดชื่อ อีเมล เบอร์ เลขบัตร เงินเดือน และ token ด้วย `<ปิด>` / `<REDACTED>` เหลือเฉพาะรหัสที่ใช้ค้น
- secret อ่านจาก environment variable เท่านั้น ห้าม hardcode หรือพิมพ์ออกมา
- production อ่านได้ เขียนไม่ได้ ถ้าจำเป็นต้องขออนุมัติพร้อมบอกจำนวนแถวที่กระทบและวิธีย้อนกลับ
- ต้องขออนุมัติก่อน: เปลี่ยน requirement หรือ business rule, ส่งข้อความหาลูกค้า, trade-off ที่กระทบ scope หรือ timeline
- เจอเรื่องที่ต้องอนุมัติ ให้หยุดเฉพาะจุดนั้น ทำส่วนที่เหลือให้จบ แล้วสรุปให้ตัดสินใจครั้งเดียว

## 8. Definition of Done

- [ ] พิสูจน์ด้วยของจริงแล้ว (test ผ่าน, query ยืนยัน, มี log หรือภาพ)
- [ ] มี negative และ edge case ไม่ใช่แค่ happy path
- [ ] สรุปปิดท้าย: แก้อะไร, เพราะอะไร, ผลที่ได้
- [ ] บอกสิ่งที่ยังไม่ได้ทำหรือทำไม่ได้ ถ้าไม่ครบให้บอกว่าข้อไหนขาด แทนคำว่า "เสร็จ"
